IMS Architecture : Foundation 01 / 06
What is a Knowledge Graph Database (IMS & AI Integration)?
Inspired by modern multi model graph architecture (SurrealDB) : how structured relationships power deterministic, hallucination free AI reasoning.
The Core Problem with Standard RAG
Traditional Vector Databases search by raw text similarity (unstructured embeddings). They find related words, but do not understand business rules, structural dependencies, or strict hierarchy : leading to AI hallucinations and out of context answers.
Knowledge Graph DB Pillars (SurrealDB Architecture)
1. Nodes & Edges
Entities (Nodes) are explicitly linked to procedures & rules via typed relationships (Edges).
2. Multi Model Graph
Combines Graph relationships + Document schemas + Full text & Vector Search in one query engine.
3. Deterministic RAG
The AI traverses verified paths (Concept → Pattern → Rule) to retrieve exact, structured context.
Why Multi Model Graph beats Pure Vector Databases
In a Knowledge Graph, relationships are first class data citizens. Instead of recalculating cosine distances across million token vector spaces, the Graph DB follows pre computed pointers (→has_pattern→governed_by) instantly. This allows LLMs to query complex multi hop dependencies without losing context.
SurrealDB Graph Retrieval Query Pattern
SELECT >has_pattern >pattern >governed_by >rule
FROM concept:cost_management
WHERE tier <= 2 PARALLEL;
Why IMS Built a Graph DB for AI
1. Full Contextual Recall
When a user asks a complex question, the AI pulls both the high level policy and deep statutory limits in a single traversal pass.
2. Zero Hallucination Bounds
Rules are hard constraints (T1 Critical). The Graph explicitly tells the LLM: "You cannot override this limit."
3. Dynamic Schema & Cross Domain Links
Connects Cost Management seamlessly to Safety, Quality, and NEC Contracts without breaking domain boundaries.
4. Sub Millisecond Pointer Traversal
Indexless adjacencies enable graph traversal in constant time $O(1)$ regardless of total database size.
Key Takeaway: The Graph Database acts as the AI's "Long Term Enterprise Memory" : converting isolated documents into an interconnected web of actionable intelligence.
Foundation: The Graph DB sets up the structural network. The following slides detail the Category vs Tier rules and the 6 Layer Op Model that govern how IMS operates.
IMS Knowledge Graph : Core Concepts 02 / 06
Category vs Tier : Two Independent Dimensions
Every node carries both a type of knowledge and a level of importance : these are orthogonal axes, not the same thing.
Category
What role does this node play?
Category describes the nature and function of a node : how the AI should use it when building a response. Each type occupies a distinct position in the reasoning chain:
● Concept : WHAT
Broad domain topics & capabilities. Parent anchors that frame the whole answer.
● Pattern : HOW WE STRUCTURE
Repeatable blueprints & delivery models. The standard shape before local changes.
● Procedure : HOW WE EXECUTE
Step by step workflows & deliverables. Where the actual work happens.
● Variant : WHERE IT DEVIATES
Regional, legal or client overrides. Localises the standard without replacing it.
● Scenario : WHEN RISK OCCURS
Real world cases & stress tests. Shows how the standard flexes under pressure.
● Rule : WHAT WE CANNOT DO
Non negotiable limits & compliance guardrails. Restricts the AI to compliant pathways.
Tier
How important is this : and how loudly should it speak?
T1 Critical T2 High T3 Standard T4 Low T5 Info
Tier controls context weight : how prominently a node appears in the AI's reasoning regardless of its depth in the graph.
⬆ Depth Promotion
A node can sit 4 levels deep in the hierarchy yet carry T1 Critical. Without tier, the AI would only encounter it after traversing many parent nodes. With T1, it is surfaced immediately : promoted above its structural position into the primary context window.

IMS Knowledge Graph : Common Question 04 / 06
Pattern vs Procedure : Aren’t They Both About “How”?
They both start with “How” : but they answer very different questions. The distinction is architecture vs action.
Pattern
The Framework
A Pattern defines the shape and architecture of how something is organised : before any work begins. It’s the repeatable model you reach for when scoping a piece of work.
It answers…
“What is our standard approach for this type of engagement?”
Example
Cost Planning Framework
Defines that cost delivery is structured around early benchmarking → control estimate → Stage 3 definitive plan. This is the template applied to every cost management engagement. You could hand it to a new joiner and they’d understand the overall shape of the work : without knowing a single specific step.
💡 Abstract : describes structure, not Tuesday’s task list. Think of it as the stage the work is performed on.
Procedure
The Workflow
A Procedure defines the specific steps you carry out within that framework — concrete, sequential, and actionable.
It answers…
“What exactly do we do, in what order, to complete this task?”
Example
Monthly Cost Report
Pull the programme → reconcile committed spend → update the forecast → apply variance commentary → submit by the 5th. These are the actual steps a team member follows. Specific, executable, in a defined order.
💡 Concrete : tells you what to do on Tuesday morning. Think of it as the performance on the stage.
Analogy : A Building Project
Pattern
“We follow RIBA stages for all construction projects” : sets the delivery structure
Procedure
“At RIBA Stage 3: run cost planning workshop → produce Stage 3 estimate → submit for approval” : the actual steps
Why both must exist in the graph
Without Patterns, all Procedures become a flat list with no sense of which delivery model they belong to. The AI knows how to run a tender evaluation but has no context that it sits within Procurement rather than Cost Management.

Without Procedures, the AI understands the shape of work but has no executable steps to reference when asked “what do we actually do?”

One Pattern typically has many Procedures beneath it : the Pattern is the container; the Procedures are the content.
If in doubt:   Pattern = “what shape does our delivery take?” (the container/framework)  —  Procedure = “what steps do we follow?” (the content/execution).   Both start with “How” : but Pattern is the architecture, Procedure is the action.
IMS Knowledge Graph : Operating Model 06 / 06
Operating Model Integration : The 6 Layers in the IMS
The Operating Model defines a 6 layer structure stack to prevent definition drift and data fragmentation. The IMS directly operationalises this stack inside the Knowledge Graph.
Layer 1 · Identifiers UUID & Node Key
Op Model: Immutable, meaningless IDs
IMS Implementation: Every node carries a permanent UUID URI. Identifiers contain zero business logic or region codes : preventing broken graph linkages when departments, regions, or service lines restructure.
⚠️ Fails when: IDs carry meaning (e.g. region codes) and break when items move.
Layer 2 · Reference Data Closed Vocabularies
Op Model: Closed permitted lists
IMS Implementation: Service lines, delivery stages, and regions are enforced enum nodes. Prevents silent vocabulary drift across offices (e.g., "Data Centre" vs "DC" vs "datacentre").
⚠️ Fails when: Permitted lists are copied into local spreadsheets and quietly drift apart.
Layer 3 · Taxonomies Concept Hierarchy
Op Model: Parent child roll ups
IMS Implementation: Parent child graph edges enforce strict lineage (Sector → Concept → Pattern → Procedure). Allows instant portfolio roll–up reporting without double counting or skipped parent levels.
⚠️ Fails when: Levels are skipped or mixed, causing portfolio totals to double–count.
Layer 4 · Relationships Graph Edges
Op Model: Cross system links
IMS Implementation: Connects Project → Person → Solution → Client via explicit graph edges rather than static PDFs. Enables multi–domain AI queries across operational silos.
⚠️ Fails when: Connections live only in text documents, making cross–project queries impossible.
Layer 5 · Schemas Mandatory Metadata
Op Model: Record rules & validation
IMS Implementation: Every node schema strictly mandates Category and Tier (T1 T5) metadata. Required fields prevent empty or unvalidated nodes from entering the AI retrieval pipeline.
⚠️ Fails when: Fields are optional, producing incomplete records that make AI context untrustworthy.
Layer 6 · Standards & Mappings Variant Mapping
Op Model: External & client alignment
IMS Implementation: Variant nodes crosswalk external client cost codes and regional statutory rules to internal standards without breaking global comparability across commissions.
⚠️ Fails when: A client's structure is adopted wholesale instead of mapped, destroying internal benchmarking.
Strategic Outcome: The IMS transforms the Operating Model from a static slide into an active, machine–enforced governance engine. It ensures business knowledge is captured once, structured globally, and retrieved flawlessly by AI.
